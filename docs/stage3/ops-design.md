## 1. Схема тестового окружения после этапа III

```
браузер ──► 127.0.0.1:8080 Nginx ─┬─ /            статика React
                                  ├─ /api/        ──► backend:8000 ──► db:5432 (сеть back, internal)
                                  └─ /media/      ──► minio:9000/kroy-products (только чтение)
                                                       backend ──► minio:9000 (запись фото)
одноразовые сервисы:  migrate (kroy_owner, перед backend)   backup (pg_dump по расписанию)
```

| Сервис | Новое | Зачем |
|---|---|---|
| `minio` | да | хранилище фото (FR-13). Образ с зафиксированной версией, том `minio_test`, healthcheck `/minio/health/live`, портов наружу нет, ключи только в `.env` |
| `migrate` | да | применяет `db/migrations/*.sql` от `kroy_owner` и завершается. Backend ждёт `service_completed_successfully` |
| `backup` | да | `pg_dump` раз в сутки и по команде, пишет в папку `./backups` на машине (вне томов Docker) |
| `backend` | изменён | `depends_on`: `migrate`, `minio`; новые переменные `MINIO_*`, `PAYMENT_PROVIDER`, `ORDER_PAYMENT_TTL_MINUTES` |
| `nginx` | изменён | `location /media/` → MinIO, только `GET`, `client_max_body_size 6m` на `/api/admin/` под загрузку фото |

Сеть: MinIO в сетях `front` (для Nginx) и `back` (для backend). Консоль MinIO (порт 9001) наружу не публикуем.

## 3. Логирование

Сейчас: одна строка на запрос (метод, путь, код, время), ошибки БД, необработанные исключения; ротация 3 × 10 МБ на контейнер; пароли и токены не пишутся (NFR-03). Добавляем:

| Что | Решение |
|---|---|
| Сквозной номер запроса | Nginx ставит `X-Request-ID` (`$request_id`), backend пишет его в каждую строку и возвращает в ответе. Ошибку из интерфейса можно найти и в логе Nginx, и в логе backend |
| События предметной области, уровень INFO | заказ создан, отменён (с причиной), истёк; платёж создан, успешен, отклонён; смена статуса админом; корректировка остатка; загрузка и удаление фото. В строке — id заказа, пользователя, платежа, без персональных данных: email, телефон и адрес не пишем |
| WARNING | отказ из-за нехватки остатка, недопустимый переход статуса, 401/403 на админских методах (по ним видно подбор доступа), повтор платежа с тем же ключом |
| ERROR | ошибка БД, MinIO недоступен, фоновая задача упала |
| Чего нет в логах | пароли, токены, заголовок `Authorization`, данные карты (их у нас и нет, NFR-09), тело запросов |
| Статус приложения | `/api/health` проверяет и БД, и MinIO: `{"status": "ok", "db": "ok", "storage": "ok", "version": "0.3.0"}`. Если MinIO недоступен, каталог продолжает работать, поэтому `storage: "unavailable"` не делает health 503, 503 только при недоступной БД |
| Где смотреть | `docker compose -f docker-compose.test.yml logs -f backend nginx`; по номеру запроса: `logs backend \| grep <request_id>` |

## 4. Резервное копирование

| Что | Как | Как часто | Сколько храним |
|---|---|---|---|
| БД | `pg_dump -Fc` (сжатый формат, восстанавливается выборочно) от `kroy_owner` | раз в сутки в 03:00 и перед каждой миграцией | 7 ежедневных + все «pre-»-копии перед релизами |
| Фото | `mc mirror minio/kroy-products ./backups/media/` | раз в сутки | одна актуальная копия |
| `.env` | не копируется скриптом: секреты хранит ответственный за стенд отдельно | — | — |

- Копии лежат в `./backups` на машине, вне томов Docker: `docker compose down -v` их не удалит. Папка в `.gitignore`.
- После каждого дампа скрипт проверяет, что он читается: `pg_restore --list`. Если нет — код выхода 1 и ERROR в логе.
- Потеря данных при аварии (RPO) — до суток, время восстановления (RTO) — около 10 минут. Для учебного стенда этого достаточно, для настоящего магазина понадобилось бы непрерывное архивирование WAL.

## 5. Восстановление

```bash
# 1. Остановить backend, чтобы в БД никто не писал
docker compose -f docker-compose.test.yml stop backend
# 2. Пересоздать пустую БД (если том потерян, compose создаст его сам при up -d db)
docker compose -f docker-compose.test.yml exec db dropdb -U kroy_owner --if-exists kroy
docker compose -f docker-compose.test.yml exec db createdb -U kroy_owner kroy
# 3. Восстановить из копии
docker compose -f docker-compose.test.yml exec -T db pg_restore -U kroy_owner -d kroy --no-owner --role=kroy_owner < backups/kroy-2026-11-05.dump
# 4. Фото
docker compose -f docker-compose.test.yml run --rm backup mc mirror ./backups/media/ minio/kroy-products
# 5. Запустить backend и проверить
docker compose -f docker-compose.test.yml start backend
```

Роль `kroy_app` хранится в кластере, а не в базе: если потерян весь том, её создаёт `03_app_role.sh` при первом запуске. Права на таблицы восстанавливаются из дампа (в нём есть `GRANT`).

Проверено на PostgreSQL 16 на копии БД после миграции V002:

| БД удалена | `database "kroy_t" does not exist` |
| Те же счётчики после восстановления | 4 / 6 / 4 / 19 / 94 |

## 6. Сценарий контролируемого отказа (№14, п.4)

**Отказ: потерян том с данными БД во время работы магазина.** Самый тяжёлый отказ для нашего стенда, и единственный, после которого без резервной копии данные не вернуть. Его же проверяет NFR-06.

| | |
|---|---|
| **Подготовка** | В магазине есть заказы: оформить 1–2 заказа, один оплатить. Записать счётчики: `orders`, `order_items`, `payments`, `stock_movements`, `sum(stock)`. Сделать копию: `run --rm backup` |
| **Как вызвать** | `docker compose -f docker-compose.test.yml down -v` — удаляет контейнеры вместе с томами (типичная ошибка: «почистил Docker»). Затем `up -d` |
| **Симптомы** | Сайт открывается, но каталог пустой; в истории заказов пусто; вход тестовыми учётками работает (seed выполнился заново), а созданных пользователей нет. В логе backend ошибок нет: формально всё «работает». `/api/health` = ok |
| **Как обнаружить** | Проверка после перезапуска: счётчики не совпали с записанными. Последний заказ по `X-Request-ID` из лога Nginx в БД не находится |
| **Причина** | `-v` удалил том `pgdata_test`, PostgreSQL создал пустую БД и выполнил `db/01_schema.sql`, `02_seed.sql` |
| **Исправление** | Восстановление по разделу 5 из копии, сделанной при подготовке |
| **Проверка** | Счётчики совпадают с записанными; заказ из подготовки виден в истории покупателя; оплаченный заказ в статусе `paid`; `schema_migrations` содержит версии 1 и 2 |
| **Что меняем, чтобы не повторилось** | В README предупреждение у `down -v`; ежедневная копия по расписанию; проверка восстановления раз в этап (этот сценарий) |

**Второй, короткий сценарий — отказ во время оформления заказа.** Остановить БД (`stop db`) в момент `POST /api/orders`. Ожидаем: ответ 503, заказ не создан, остаток не изменился (транзакция откатилась целиком), после `start db` оформление проходит. Этот сценарий проверяет, что резерв и заказ создаются атомарно (NFR-08).
