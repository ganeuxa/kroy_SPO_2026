## 2. Резервирование и возврат остатков (вопрос №1, NFR-08)

**Решение: товар списывается со склада в момент оформления заказа** (это и есть резерв). При отмене или истечении срока оплаты списанное возвращается. Отдельную колонку `reserved` не заводим: тогда остаток для покупателя пришлось бы везде считать как `stock - reserved`, и любой забытый запрос показал бы неправильное наличие.

Оформление заказа — одна транзакция:

```sql
-- 1. Блокируем позиции корзины пользователя
SELECT ... FROM cart_items WHERE user_id = :user FOR UPDATE;
-- 2. Для каждого варианта по возрастанию id (одинаковый порядок исключает взаимную блокировку):
UPDATE product_variants
SET stock = stock - :qty, updated_at = now()
WHERE id = :variant_id AND is_active AND stock >= :qty
RETURNING stock;
--    0 строк → ROLLBACK и 409 «Недостаточно товара: <название>, в наличии N шт.»
-- 3. INSERT INTO orders (..., status = 'new', expires_at = now() + interval '15 minutes')
-- 4. INSERT INTO order_items (... price_at_purchase = products.price)
-- 5. INSERT INTO stock_movements (variant_id, delta = -:qty, reason = 'reserve', order_id)
-- 6. INSERT INTO order_status_history (order_id, NULL, 'new', changed_by = :user)
-- 7. DELETE FROM cart_items WHERE user_id = :user
COMMIT;
```

Почему это защищает последнюю единицу. `UPDATE` с условием `stock >= :qty` берёт блокировку строки варианта. Второй покупатель ждёт, пока первая транзакция закончится, затем PostgreSQL перепроверяет условие уже по новому остатку, находит `stock = 0` и обновляет 0 строк. Даже если в коде будет ошибка, отрицательный остаток не запишется из-за `CHECK (stock >= 0)`.

Проверено на копии БД этапа II (две сессии `kroy_app`, остаток 1):

| Проверка | Результат |
|---|---|
| Сессия A списала 1 шт. и держит транзакцию 2 с | `reserved, left 0` |
| Сессия B в это время списывает ту же штуку | ждала 1,5 с, затем 0 строк, то есть отказ |
| Остаток после обеих | 0, не −1 |

**Возврат.** При отмене (покупателем, админом, по сроку оплаты) в одной транзакции:

```sql
UPDATE orders SET status = 'cancelled', cancel_reason = :reason, updated_at = now()
WHERE id = :order AND status IN (<допустимые>) RETURNING id;   -- 0 строк → 409
-- возвращаем ровно то, что было списано под этот заказ, по журналу:
INSERT INTO stock_movements (variant_id, delta, reason, order_id)
SELECT variant_id, -SUM(delta), 'release', order_id
FROM stock_movements WHERE order_id = :order GROUP BY variant_id, order_id HAVING SUM(delta) < 0;
UPDATE product_variants v SET stock = v.stock + r.qty FROM (<то же>) r WHERE v.id = r.variant_id;
INSERT INTO order_status_history (...);
```

Возврат по журналу, а не по `order_items`, по двум причинам. Повторная отмена ничего не вернёт дважды: сумма по заказу уже 0. А старые заказы из seed, под которые остаток никогда не списывался, не «добавят» на склад лишние штуки.

**Срок оплаты.** `expires_at = created_at + 15 минут`, значение задаётся настройкой `ORDER_PAYMENT_TTL_MINUTES`. Фоновая задача в backend раз в минуту отменяет просроченные:

```sql
SELECT id FROM orders WHERE status = 'new' AND expires_at < now()
ORDER BY expires_at LIMIT 50 FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED` позволяет запустить несколько копий backend: они не будут отменять один заказ одновременно. Кроме того, оплата просроченного заказа отклоняется сразу, не дожидаясь задачи (409).

## 3. Статусы заказа (FR-15)

| Из | В | Кто | Остаток |
|---|---|---|---|
| — | `new` | покупатель, оформление | списывается (`reserve`) |
| `new` | `paid` | система, после успешного платежа | — |
| `new` | `cancelled` | покупатель, админ, система по сроку | возвращается (`release`) |
| `paid` | `shipped` | админ | — |
| `paid` | `cancelled` | админ (возврат денег в тестовом режиме) | возвращается |
| `shipped` | `delivered` | админ | — |

Любой другой переход — 409 «Нельзя перевести заказ из статуса X в Y». Каждый переход пишется в `order_status_history` (`changed_by = NULL` у системных). Набор статусов в `CHECK` не меняется, поэтому данные этапа II остаются корректными.

## 4. Самовывоз и адрес (вопрос №6)

Ошибка этапа I: `delivery_address NOT NULL` при любом способе доставки, поэтому при самовывозе в адрес писали текст пункта выдачи. Теперь:

- пункты выдачи — справочник `pickup_points`, фронт берёт список из `GET /api/pickup-points`;
- `CHECK chk_orders_delivery`: курьер → обязателен `delivery_address`, `pickup_point_id` пустой; самовывоз → наоборот;
- миграция переносит текст адреса из старых заказов с самовывозом в `pickup_points` и проставляет ссылку, ни один заказ не теряется.

## 5. Платежи: идемпотентность и тестовый режим (вопрос №7, NFR-09)

Платёжный сервис работает в тестовом режиме: это эмулятор внутри backend (`PAYMENT_PROVIDER=test`). Настоящему сервису (например, ЮKassa) нужен публичный адрес для уведомлений, а наш стенд не публичный. Интерфейс эмулятора повторяет схему настоящего сервиса, поэтому позже его можно заменить без изменения таблиц.

1. Фронт создаёт платёж: `POST /api/orders/{id}/payments` с заголовком `Idempotency-Key: <UUID>`. Ключ генерируется один раз на нажатие «Оплатить».
2. Backend создаёт `payments` со статусом `pending` и отдаёт `confirmation_url` — страницу платёжного сервиса.
3. Карту покупатель вводит только на странице сервиса. У нас в БД и логах номера карты нет: колонок для неё нет вообще (NFR-09).
4. Сервис сообщает результат. В тестовом режиме это `POST /api/test-provider/payments/{provider_payment_id}`: `succeeded` переводит заказ в `paid`, `failed` записывает `failure_reason`, и заказ ждёт новой попытки до `expires_at`.

Защита от двойной оплаты:

| Ситуация | Что не даёт ошибиться |
|---|---|
| Двойной клик, повтор запроса после обрыва сети | тот же `Idempotency-Key` → `UNIQUE (order_id, idempotency_key)`, возвращаем уже созданный платёж с кодом 200 |
| Две вкладки с разными ключами | частичный уникальный индекс: один `pending` на заказ → 409 |
| Повторное уведомление сервиса об успехе | частичный уникальный индекс: один `succeeded` на заказ; повтор ничего не меняет |
| Оплата после истечения срока или отмены | проверка `status = 'new' AND expires_at > now()` с блокировкой заказа → 409 |

## 6. Варианты и фото в MinIO (вопрос №3, FR-13, FR-14)

- Вариант (размер + цвет) нельзя удалить: на него ссылаются `order_items`. Его скрывают через `is_active = false`, и в каталоге и корзине он больше не предлагается.
- Остаток админ меняет не «установкой числа», а корректировкой `+N / −N` (`reason = 'adjust'`, `changed_by` = админ). Так правка не затрёт резерв, сделанный покупателем в ту же секунду, а журнал показывает, кто и когда менял остаток.
- Фото лежат в MinIO, бакет `kroy-products`, ключ `products/{product_id}/{uuid}.{jpg|png|webp}`. В БД — только ключ, тип и размер.
- Загрузка идёт через backend: он проверяет тип (JPEG, PNG, WebP по сигнатуре файла, а не по расширению) и размер до 5 МБ (`CHECK size_bytes`), кладёт файл в MinIO и только потом пишет строку. Если запись в БД не удалась, файл удаляется.
- Отдача: Nginx проксирует `/media/` на MinIO (только чтение, только этот бакет), API отдаёт готовый `image_url = /media/<ключ>`. MinIO наружу не открыт.
- Цвет у фото необязателен: общий снимок товара может не относиться к одному цвету. Если цвет указан, backend проверяет, что у товара есть вариант такого цвета.

Новые таблицы получают `SELECT, INSERT, UPDATE` для `kroy_app` автоматически (`ALTER DEFAULT PRIVILEGES` из `03_app_role.sh`). ## 8. Механизм миграций

Сейчас схема создаётся только при первом запуске тома БД. Существующую базу так не обновить: пришлось бы удалять данные.

- Файлы `db/migrations/V{номер}__{имя}.sql`, у каждого своя транзакция.
- Таблица `schema_migrations`: номер, имя, sha256 файла, время применения. Версия 1 — схема этапов I–II, для существующих БД она записывается как уже применённая.
- Короткий скрипт `backend/app/migrate.py` применяет по порядку только новые файлы и останавливается, если у уже применённого файла изменилась контрольная сумма.
- В compose отдельный одноразовый сервис `migrate` запускается от `kroy_owner` (у `kroy_app` нет прав на DDL). Backend стартует после него: `depends_on: migrate: condition: service_completed_successfully`.
- Перед миграцией на стенде обязательно делается резервная копия (см. `ops-design.md`).

Alembic не берём: источник истины у нас — SQL-схема из отчёта №4, а не модели SQLAlchemy, и автогенерация миграций здесь больше мешала бы.
